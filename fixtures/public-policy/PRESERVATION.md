# Public source and test preservation policy

This is a machine acceptance constraint in addition to the assigned feature contract. Passing behavioral tests alone is insufficient. These rules are supplied equally to every implementation agent and supervisor before dispatch. The exact original-test predicate is the readable `preservation/preserve-tests.mjs` beside this document; it uses TypeScript 5.9.3. The independently frozen evaluator runs the same predicate against the original baseline. There is no semantic human-review override in core acceptance.

## Application source and scope

The assigned task remains the authority for feature behavior. An allowed file path does not authorize unrelated changes, an auth/seed/schema change, or another task.

- Existing non-test source that the finite path gate permits changing: `server/app.ts`, `server/db.ts`, `src/main.tsx`, `src/style.css`.
- New source files may be under `src/` or `server/` ending in `.ts`, `.tsx`, `.css`; new test files may be under `tests/` ending in `.ts`, `.tsx`, `.js`, `.jsx`, `.css`. The relative path alphabet is ASCII letters, digits, underscore, dot, slash and hyphen. Original file deletion, symlinks and nonregular files fail.
- Other existing files are frozen: package/lock, compiler/linter/build/test configuration, HTML, README and reset/seed files. Dependencies cannot change unless a task-specific public migration and matching evaluator amendment were frozen before dispatch. The calibration C2/C3/C4 contracts authorize no dependency, auth, API-schema or database-schema changes. C2 alone adds the specified sort query behavior; C3/C4 preserve their stated API behavior.
- Host-generated overlays and regenerable dependencies, caches, build output and disposable databases are removed from source-only inventory according to the assigned public inventory manifest. This does not authorize editing task/FAQ/spec or other immutable supplied material. Endpoint integrity and overlay hashes are checked separately.

## Original tests: exact finite limits

Original test files and their original statements, assertions, imports, helpers, hooks, control flow, comments and ordering must be retained byte-for-byte after removal of only the additions admitted below. A semantically reasonable change outside this finite relation is still rejected. Preserve original test bodies except the narrow legacy seed-site exception below; adding assertions inside any other original test body is unsupported.

1. New ordinary test cases can be inserted at eligible direct statement boundaries in an existing ordinary `describe` group. The group and case calls are bare identifiers with exactly two arguments: a string-literal title and an arrow or non-generator function with a block body. No modifiers (`only`, `skip`, etc.), optional calls or type arguments. Groups must be direct top-level groups or directly nested existing groups and have unambiguous title paths. Do not insert a group inside an original test body.
2. Up to16 new group cases per original file; each nonempty case title must differ from all original plain case titles in that file and all other added titles. At least one adjacent original statement must be a plain `test`; the other neighbor must be a plain `test` or the group edge. No insertion next to a hook or non-test statement. Original boundary trivia must be whitespace and survive as an exact prefix or suffix; new surrounding trivia must be whitespace. Multiple adjacent new cases are supported. New case bodies are parsed but their runtime safety is not certified by preservation.
3. `tests/api.test.ts` additionally supports up to16 top-level cases after all original top-level statements, but ONLY the exact small `newCase` regular-expression grammar in the supplied module. This is not permission for arbitrary new top-level test bodies: its GET-only Bruno `/api/me` numeric count/length assertions, names, formatting and statement sequence are exact. No other original file permits top-level additions under this exception.
4. The module retains a narrow C1 legacy exception at the original `seed and sorted membership across roles` case in `tests/api.test.ts`: its one exact optional workspace-ID-to-ID-plus-count expectation migration (`OLD`/`MIGRATED`) and up to16 exact numeric assertions at the end of that seed case, as specified by `assertion`. It does NOT permit changes or in-case additions elsewhere. It is not authorization to implement C1 in another assigned task. Any new task-specific compatibility migration must be explicitly public and evaluator-bound before dispatch; none is implicit in a broad FAQ statement.
5. Comments at insertion boundaries, reformatting, other assertion APIs or positions, renamed original tests, duplicate titles, extra imports/helpers/hooks, reordered or removed original statements, altered timeouts and arbitrary original-body changes are outside this finite relation. Original test syntax must parse. Read the supplied module for exact whitespace and structural checks; a prose approximation does not expand the rule.

New test files under the allowed path filter do not replace original or trusted regression tests. All targeted and full checks remain required. The source gate does not prove semantic equivalence or test safety; independent external regression, feature, authentication, database and artifact-integrity checks remain mandatory. If an unsupported transformation is needed, report the constraint honestly; an operator will not silently waive it after observing your result.

## Publication and admission

This public policy is a prospective disclosure of the finite gate, not a change to earlier outcomes. A task packet is not admitted until a fresh authorized-model review confirms its public contract, FAQ, allowed migrations, source predicate and reference/alternative checks agree. Every role receives identical policy bytes and the policy hash is in the manifest. Sealed behavioral cases may test disclosed behavior but must not introduce an undisclosed source-edit requirement.
